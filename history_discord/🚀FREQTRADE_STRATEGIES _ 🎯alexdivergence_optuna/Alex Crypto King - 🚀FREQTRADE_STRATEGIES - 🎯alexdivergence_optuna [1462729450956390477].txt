[01/19/2026 09:57] lukovicka
This is a classic SQLite concurrency issue. The `database is locked` error occurs because SQLite has limited support for concurrent writes, and your background threads are competing for database access.
Root causes:

Multiple pairs triggering optimization simultaneously via `threading.Thread`
Each `trial.suggest_*` call writes to the SQLite database
SQLite's default timeout (5 seconds) is too short for heavy optimization loads

**Solutions (pick one or combine)**:

**Option 1: Quick Fix — SQLite Connection Args + WAL Mode**
```python
# In optimize_coin method, modify storage creation:
storage_path = f"sqlite:///{study_dir}/optuna_{study_name}.db?timeout=60"

# Better: Use RDBStorage with engine_kwargs
from optuna.storages import RDBStorage

storage = RDBStorage(
    url=f"sqlite:///{study_dir}/optuna_{study_name}.db",
    engine_kwargs={
        "connect_args": {
            "timeout": 60,
            "check_same_thread": False
        },
        "pool_pre_ping": True,
    }
)

# Enable WAL mode (add after study creation)
import sqlite3
db_path = f"{study_dir}/optuna_{study_name}.db"
conn = sqlite3.connect(db_path)
conn.execute("PRAGMA journal_mode=WAL;")
conn.close()
```

**Option 2: Add Optimization Lock (Recommended)**
Add a global lock to serialize optimizations:
```python
class RealOptunaManager:
    _optimization_lock = threading.Lock()  # Class-level lock
    
    def optimize_coin(self, pair: str, objective_func, n_trials: int = 60):
        # Serialize all optimizations
        with self._optimization_lock:
            # ... existing optimization code ...
```

**Recommendation**: Combine **Option 1 + Option 2**. The lock ensures no parallel SQLite writes, and the connection args provide safety if something slips through.
